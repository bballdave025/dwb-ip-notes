# Vision — Learn Stochastic Decision-Making by Playing WarGear

**Date:** 2026-11-19
**Status:** non-binding roadmap, not a project deadline

## One-paragraph positioning

Use an enjoyable Risk-style game as a laboratory for learning stochastic modeling: reconstruct what happened from screenshots and history, calculate local probabilities exactly where feasible, check the math with simulation, and gradually learn to evaluate decisions through Markov decision processes. The end product should primarily be better *human* mathematical intuition, with reproducible Python examples useful for optional upskilling.

## Why this is worthwhile

Real games supply motivating questions: Is an attack likely to succeed? How costly is a failure? When is a valuable opportunity not worth taking? Which state variables matter? What changes when the opponent is adaptive? These create natural transitions from basic probability to absorbing Markov chains, simulations, policy choice, and partially observed strategic models.

## Learning sequence

### 0. Data intake (current)
- Preserve screenshot order and text history; reproduce the official history text without overinterpretation.
- Distinguish event-history IDs from player-turn counts.
- Capture board-specific rules and important geometry.
- Record ambiguities openly; omit unverified state values.
- Write small, readable parsing/transformation scripts later if useful; this should not turn into a computer-vision engineering project.

### 1. Dice and finite-state battle models
- Enumerate legal dice outcomes under the verified WarGear rules.
- Define attacker/defender army-count states and transition probabilities.
- Compute eventual success/failure probabilities and expected losses using absorbing-chain mathematics.
- Simulate battles with Monte Carlo and compare estimates and confidence intervals to exact values.
- Explain why simulation and exact chains are related but not identical methods.

### 2. Decision-aware models
- Describe legal available actions and decisions to continue/stop an attack.
- Introduce a reward or utility function and Bellman recursion.
- Inspect assumptions: immediate win probability is not the same as strategic value.
- Prefer interpretive explanations and self-prediction exercises over an automated best-move command.

### 3. Full-board strategy (optional)
- Formalize territory ownership, army counts, income/bonuses, cards, fog, and turn order.
- Explore spatial adjacency, choke points, defense, and longer horizons.
- Discuss opponent uncertainty and the limits of the Markov assumption.
- Compare policies or limited-depth Monte Carlo tree search only as motivated by a concrete question.

### 4. Teaching / sharing (optional)
- Turn useful demonstrations into notebooks with short exercises and plots.
- Allow a newcomer to supply one board situation, predict the outcome, and then see the model's result.
- Share learning material with interested Boston/Utah friends without making this a standing obligation.

## Canonical evidence structure

The eventual machine-readable event record should retain:
- game identifier and board/rules version, when verified;
- event ID, actor, action type, event text, optional timestamp;
- source/destination territory names and players when explicitly grounded;
- raw dice text distinct from parsed rolls;
- before/after state when observed;
- screenshot source reference(s), confidence, and unresolved questions.

Maintain raw source evidence separately. An optional API adapter should produce the same canonical records rather than dictate analysis-code structure. The availability and membership requirements of the API are **unverified**.
